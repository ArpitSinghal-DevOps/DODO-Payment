# Task 2 - Build, Scan, Sign, Attest, and Deploy

## Objective

Promote `ledger-api` from a local-only image to a verifiable supply-chain workflow.

Task 2 adds GitHub Actions automation that builds the container, blocks high-risk vulnerabilities, publishes immutable GHCR tags, signs the image with keyless Sigstore identity, creates SBOM and provenance attestations, and gives GitOps manifests for deploying the promoted image.

## Files

- `.github/workflows/task2-supply-chain.yml`: CI/CD pipeline for build, scan, publish, sign, SBOM, and provenance.
- `task2/gitops/overlays/prod/kustomization.yaml`: production-style Kustomize overlay that consumes the Task 1 base and swaps the local image for GHCR.
- `task2/gitops/overlays/prod/README.md`: promotion instructions for updating the image tag or digest.

## Pipeline Controls

`pull_request`: builds and scans the image locally without pushing.

`push` to `main` or version tags: builds, scans, pushes to GHCR, signs the pushed digest, attaches an SPDX SBOM attestation, and publishes build provenance.

`id-token: write`: required for keyless signing and GitHub provenance attestations.

`packages: write`: required to push to GitHub Container Registry.

`security-events: write`: required to upload Trivy SARIF evidence to GitHub code scanning.

`docker/metadata-action`: emits immutable tags such as `sha-<commit>` and release tags. The workflow intentionally does not publish `latest`.

`Trivy`: fails on high and critical OS or library vulnerabilities. This is expected to fail until the vulnerable demo app dependencies are remediated in a later application-security task.

`Cosign`: signs the published image digest with GitHub OIDC identity. This supports the Kyverno signed-image policy in Task 1.

`SBOM`: records package inventory as SPDX JSON and attaches it as an image attestation.

`Build provenance`: publishes a verifiable GitHub attestation tying the image digest back to the workflow run.

## GitOps Promotion

Render the production overlay:

```bash
kubectl kustomize task2/gitops/overlays/prod
```

After the workflow publishes a successful image, update the overlay image tag:

```bash
cd task2/gitops/overlays/prod
kustomize edit set image ledger-api=ghcr.io/<owner>/ledger-api:sha-<commit>
```

Apply after review:

```bash
kubectl apply -k task2/gitops/overlays/prod
```

For stricter production promotion, replace the tag with a digest reference generated by the workflow:

```bash
kustomize edit set image ledger-api=ghcr.io/<owner>/ledger-api@sha256:<digest>
```

## Verification

Local structural verification:

```bash
kubectl kustomize task2/gitops/overlays/prod
```

Cluster verification after applying a promoted image:

```bash
kubectl -n payments rollout status deploy/ledger-api
kubectl -n payments get deploy ledger-api -o jsonpath='{.spec.template.spec.containers[0].image}'
kubectl -n payments get pods
```

Signature verification for a published digest:

```bash
cosign verify \
  --certificate-identity 'https://github.com/<owner>/<repo>/.github/workflows/task2-supply-chain.yml@refs/heads/main' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  ghcr.io/<owner>/ledger-api@sha256:<digest>
```

Attestation verification:

```bash
cosign verify-attestation \
  --type spdx \
  --certificate-identity 'https://github.com/<owner>/<repo>/.github/workflows/task2-supply-chain.yml@refs/heads/main' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
  ghcr.io/<owner>/ledger-api@sha256:<digest>
```

## Expected Current Result

The pipeline is intentionally strict. With the current demo app, Trivy is likely to fail because the Dockerfile and Python requirements use old vulnerable versions. That is a correct Task 2 control, not a CI bug.

## Closeout

Task 2 creates the release path and supply-chain evidence. The next application-security task should remediate the vulnerable runtime and dependencies so the Trivy gate passes consistently.
